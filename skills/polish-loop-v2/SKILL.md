# Polish Loop V2 — 精准审查

基于实战教训重构的审查流程。核心改进：**硬性轮次上限、回归守卫、变更聚焦、去重检查**。

## 配套脚本

- `scripts/duplicate-check.sh [DIRECTORY]`：查找同名文件/重复模块（去重检查）。
- 运行时基线验证需结合项目自身编译/启动/测试命令执行。

---

## 第 0 步：软件基线检查（必须在任何审查之前执行）

在开始代码审查之前，先验证软件的基本功能是否完整。如果基线不通过，**不要做代码审查，先修基线**。

### 通用基线

```
□ 能启动（不崩溃、不白屏）
□ 核心流程可走通（登录 → 主页 → 查看 → 创建 → 返回）
□ 有错误提示（出错时用户知道发生了什么）
□ 有加载状态（等待时用户知道在加载）
□ 有空状态（没数据时用户知道该做什么）
```

### Web 应用额外

```
□ 所有路由有对应页面（不 404）
□ 受保护路由有 auth guard
□ 刷新页面不丢失状态
```

### 桌面应用额外

```
□ 窗口能打开（不崩溃）
□ 外部链接在浏览器打开
□ 关闭窗口后进程退出
```

**关键规则：每轮修复后必须重新走一遍基线流程。基线被破坏时立即停止当前轮次，优先修复基线。**

---

## 实战教训

1. **无限迭代的陷阱**：没有硬性轮次上限会导致永远无法宣布 CLEAN。修正：每轮只审查上轮变更 + 回归检查。
2. **修复引入新 bug**：修复时可能破坏已有功能。修正：每轮开始前执行去重检查，修复后执行回归验证。
3. **全量审查效率递减**：全量扫描会导致"越查越多"。修正：第 1 轮全量建立基线，后续仅审查变更文件。

## 完整工作流

### Phase 0: 准备

```
1. 确认 git 工作区干净
2. 记录项目类型和验证命令（编译、启动、测试）
3. 执行去重检查：scripts/duplicate-check.sh
4. 建立回归检查清单
```

### Phase 1: 第 1 轮 — 全量基线扫描

仅第 1 轮做全量扫描。审查内容：
1. 编译检查
2. 读取所有源文件
3. 去重检查：查找同名文件、重复模块、死代码文件
4. 交叉验证：前后端 API 契约、IPC 通道、CSS 类引用

问题分级：
- **CRITICAL**: 编译失败 / 启动崩溃 / 无法运行
- **HIGH**: 运行时错误 / 功能损坏
- **MEDIUM**: 逻辑 bug / UX 问题
- **LOW**: 代码质量 / 风格问题

修复所有 CRITICAL + HIGH，提交。记录修改的文件列表。

### Phase 2: 后续轮次 — 变更聚焦 + 回归

**硬性上限：最多 5 轮（含第 1 轮）。**

每轮执行：

```
1. 回归验证（先验证再审查）：
   - 运行编译命令
   - 启动应用，走通核心流程
   - 确认上轮修复仍然有效
   - 回归失败 → 立即修复，不进入审查

2. 变更审查（仅审查上轮修改的文件）：
   git diff --name-only HEAD~1

3. 修复 + 提交
4. 更新回归检查清单
```

### Phase 3: 收敛判断

**停止条件（满足任一即停止）：**
- 达到 5 轮上限
- 连续 2 轮无 CRITICAL/HIGH 问题
- 回归验证全部通过 + 剩余问题全是 LOW
- 用户主动停止

**不要继续的信号：**
- 连续两轮发现相同类型的问题 → 审查范围需要收窄
- 问题数不降反升 → 修复引入了新问题，需暂停并人工审查

### Phase 4: 最终报告

```markdown
## 审查完成

**N 轮审查，累计修复 M 个问题：**

| 轮次 | 范围 | CRITICAL | HIGH | MEDIUM | LOW | 回归 |
|------|------|----------|------|--------|-----|------|
| 1    | 全量 | 2        | 5    | 8      | 6   | —    |
| 2    | 变更 | 0        | 1    | 3      | 2   | ✅   |

**回归检查清单：**
- [x] 应用能启动
- [x] 核心流程可走通
```

## 关键规则

### 审查 prompt 设计

**第 1 轮（全量）：** 读取所有源文件、查找同名文件、交叉验证前后端契约

**后续轮次（变更聚焦）：** 仅审查 `git diff --name-only HEAD~1` 列出的文件，不要审查未修改的文件

### 修复 prompt 设计

- 先读取每个要修改的文件
- 只做被要求的修复
- 修复后运行编译检查

### 回归检查清单

每轮修复后，将修复的 bug 转化为回归检查项：
- 修复了 "DB 连接泄漏" → 添加 "创建 session 后能正常返回数据"
- 修复了 "路由缺失" → 添加 "对应页面能正常显示"

### 去重检查

每轮开始前执行 `scripts/duplicate-check.sh`，发现同名文件时确认是否为重复模块。
